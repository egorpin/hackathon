# HTTPS и WSS в автономной LAN

Для сервера в WSL и клиентов Windows 11 подготовлен
[запуск с Windows mDNS-утилитой и единым адресом mars.local](windows-lan.md).

Браузеры подключаются к `https://<IPv4-сервера>:8443`, WebSocket автоматически
использует `wss://<IPv4-сервера>:8443/ws`. TLS завершается в Nginx. API и WebSocket
между Nginx и FastAPI идут по внутренней Docker-сети; backend не публикует порт
на LAN. Cookie сессии получает флаги `Secure`, `HttpOnly` и `SameSite`.

HTTPS работает без интернета, DNS и публичного домена. Для HTTPS-страницы нужен
WSS: браузер блокирует обычный `ws://` как mixed content. Дополнительное
шифрование сообщений поверх WSS не требуется: TLS защищает cookie, чат и команды.

## Подготовка до демонстрации

Если IPv4 меняется при переходе между точками доступа, используйте
[постоянное имя сервера](#постоянное-имя-вместо-ipv4). Тогда перевыпускать
сертификат при смене IP не потребуется. Ни клиент, ни backend не содержат
фиксированного LAN-IP: клиент берёт API и WebSocket с адреса открытой страницы.

На сервере нужны Docker Desktop с Linux containers, Python 3 и OpenSSL.
Генератор на Windows также находит OpenSSL из стандартной установки Git for Windows.
Python и OpenSSL нужны только при выпуске сертификатов. На клиентах нужен браузер.

1. Выполните `ipconfig` на сервере и возьмите IPv4 активного Ethernet/Wi-Fi адаптера
   сети демонстрации, например `192.168.1.10`. Адрес WSL, Docker или VPN не подходит.
   Закрепите IPv4 через DHCP роутера либо настройте статический адрес.
2. Пока интернет доступен, соберите production-образы:

   ```powershell
   docker compose -f compose.https.yaml build
   ```

3. Выпустите локальный CA и сертификат сервера, интернет для этого не нужен:

   ```powershell
   py tools/generate-lan-cert.py 192.168.1.10
   ```

   На Linux используйте `python3` вместо `py`. Можно перечислить несколько IPv4
   через пробел. В SAN также включены `localhost` и `127.0.0.1`.
   Создаются `certs/ca.crt`, `certs/ca.key`, `certs/server.crt`, `certs/server.key`.
   CA действует 10 лет, серверный сертификат — 365 дней.
   При повторном запуске CA сохраняется, сертификат сервера перевыпускается.
   При подключении по IP после его смены повторите команду с новым адресом и пересоздайте контейнер клиента
   командой, которую выводит скрипт. CA заново устанавливать не требуется.
   Проверьте дату и время на компьютерах.
4. Передайте **только `ca.crt`** на каждый клиент и установите его в доверенные
   корневые центры сертификации текущего пользователя Windows:

   ```powershell
   certutil -user -addstore Root .\ca.crt
   ```

   Установите CA также на сервере, если на нём открыт браузер; из корня проекта
   путь — `certs\ca.crt`. Перезапустите браузер. Edge/Chrome используют хранилище
   Windows. Если Firefox не доверяет сертификату, импортируйте `ca.crt` в его
   настройках сертификатов: Центры сертификации → Импортировать → доверять для
   идентификации сайтов. Ключи `*.key` остаются на сервере. Каталог `certs`
   исключён из Git и контекста сборки; в Nginx подключены только ключ и сертификат сервера.
5. Разрешите входящий TCP-порт 8443 на сервере в частной сети Windows.
   Гостевой Wi-Fi с client isolation не подходит: клиенты должны видеть сервер.
   Для другого порта задайте `MARS_HTTPS_PORT` в `.env` и разрешите его в firewall.
   Из-за смены порта менять сертификат не требуется.

## Постоянное имя вместо IPv4

Выпустите сертификат на имя один раз:

```powershell
py tools/generate-lan-cert.py --hostname mars.home.arpa
```

CA устанавливается на клиентах так же, как в варианте с IP. Открывайте
`https://mars.home.arpa:8443`; клиент автоматически подключается к
`wss://mars.home.arpa:8443/ws`. При смене IP сертификат и настройки приложения
остаются прежними. Сертификат всё равно нужно обновлять по окончании его срока
действия или при смене имени.

**Имя должно разрешаться внутри LAN.** Генератор сертификатов не настраивает DNS
и не объявляет сервер в сети. Есть три варианта:

| Способ | Что происходит при смене точки доступа/IP |
| --- | --- |
| Локальный DNS роутера: `mars.home.arpa` → IP сервера | Обновите запись на новом роутере либо настройте интеграцию DHCP/DNS, если роутер её поддерживает. Клиенты должны использовать этот локальный DNS. |
| mDNS: например `mars.local` | Настроенный на сервере mDNS-ответчик объявляет текущий IP без DNS роутера. Клиенты должны поддерживать mDNS; multicast и UDP 5353 должны быть разрешены в LAN. |
| Файл `hosts` на каждом клиенте | После смены IP обновите запись на каждом компьютере. Это ручной резервный вариант; сертификат остаётся прежним. |

Для частой смены точек доступа удобен mDNS, если он поддерживается компьютерами
и сетью. Для него используйте сертификат с нужным именем:

```powershell
py tools/generate-lan-cert.py --hostname mars.local
```

Ответчик должен работать на ОС сервера с LAN-интерфейсом, например Avahi на Linux
или настроенная служба Bonjour на Windows. Сам Nginx в Docker Desktop не объявляет
`mars.local`; используйте [Windows-утилиту проекта](windows-lan.md). Сеть с client isolation или
запретом multicast может мешать mDNS. Суффикс `.local` предназначен для mDNS,
а `home.arpa` — для локального DNS.

Проверить имя на Windows можно командой:

```powershell
Test-NetConnection mars.home.arpa -Port 8443
```

В ручном варианте добавьте строку вида `192.168.1.10 mars.home.arpa` в
`C:\Windows\System32\drivers\etc\hosts` на каждом клиенте с правами администратора.
После смены IP обновите её. Внешний DNS и интернет не нужны ни одному из вариантов.

Можно включить несколько имён и IP в один сертификат:

```powershell
py tools/generate-lan-cert.py 192.168.1.10 --hostname mars.home.arpa --hostname mars.local
```

Проверка HTTPS/WSS по имени:

```powershell
py tools/check-https.py https://mars.home.arpa:8443 --ca certs/ca.crt
```

При переходе между сетями корневой CA на клиентах повторно устанавливать не нужно.

## Запуск во время показа

Отключите WAN у роутера/точки доступа, сохранив LAN. Отключите альтернативные
каналы интернета на всех компьютерах: мобильную сеть, второй Wi-Fi и VPN.
Так автономно работает весь компьютер, включая браузер, ОС и Docker Desktop.

На Windows запустите из корня проекта `start-https.cmd`. Эквивалентная команда:

```powershell
docker compose -f compose.https.yaml up -d --no-build --pull never --remove-orphans --wait
```

Эта команда не собирает образы, не устанавливает пакеты и не загружает образы.
Внешний центр сертификации не используется. Backend подключён только к сети
`internal: true` без внешнего маршрута. Nginx также подключён к обычной bridge-сети,
чтобы Docker Desktop мог публиковать HTTPS-порт в LAN. Для автономности всех
компьютеров WAN должен быть отключён, как описано выше. Frontend и ассеты
загружаются из production-образа на LAN-сервере.

Откройте `https://192.168.1.10:8443` на каждом клиенте. Не обходите предупреждения
сертификата: при установленном CA и IP из SAN их быть не должно. Origin страницы
проверяется сервером автоматически, добавлять каждый LAN-IP в `.env` не нужно.

Это самостоятельный Compose-файл: не объединяйте его с `compose.yaml` или
`compose.prod.yaml` через несколько `-f`. Имя проекта и volume `mars-data`
совпадают с обычным запуском: контейнеры заменяются, игровой прогресс сохраняется.
Не используйте `down -v`, если нужно сохранить мир.

Для переноса образов на другой сервер заранее выполните:

```powershell
docker image save -o mars-colony-images.tar mars-colony-server:local mars-colony-client:local
```

На целевом сервере нужны файлы проекта, сертификат для используемого имени/IP и импорт образов
`docker image load -i mars-colony-images.tar`. Существующий SQLite volume
переносится отдельно, если нужно сохранить игру.

## Проверка

После отключения WAN проверьте на каждом компьютере страницу, регистрацию, вход,
чат, начало экспедиции, движение игроков и восстановление после F5.
В DevTools → Network соединение `/ws` должно иметь URL `wss://…` и статус 101,
все ресурсы должны загружаться с LAN-сервера. В консоли не должно быть ошибок
сертификатов и mixed content.

Автоматический тест создаёт игрока и отправляет сообщение в чат. Запускайте его
на отдельном тестовом мире, заранее установив `server/requirements-dev.txt`:

```powershell
py tools/check-https.py https://127.0.0.1:8443 --ca certs/ca.crt
```

Он проверяет доверенную цепочку и имя сервера без отключения проверки TLS,
cookie `Secure`, авторизацию, запрет постороннего Origin и повторное подключение WSS.
Автономность всей демонстрации проверяется при отключённом WAN.

Документация: [Nginx TLS](https://nginx.org/en/docs/http/configuring_https_servers.html),
[OpenSSL](https://docs.openssl.org/3.2/man1/openssl-req/),
[WebSocket и mixed content](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_client_applications),
[home.arpa (RFC 8375)](https://www.rfc-editor.org/rfc/rfc8375.html),
[mDNS (RFC 6762)](https://www.rfc-editor.org/rfc/rfc6762).
